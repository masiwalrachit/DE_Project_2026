## 3. Growth analysis

- **Stayed about the same (≤3×):** R01, R02, R06, R07, R10, R13, R23, R24, W01, W02, W03. These are selective PK/UNIQUE/composite-index lookups, fixed-size results, or sub-millisecond operations where cache noise is larger than the real growth.
- **Grew with the dataset (>3× to 25×):** R03, R04, R05, R08, R09, R11, R14, R15, R16, R17, R19, R20, R22, R25. These read a fixed date range, a fixed share, or a whole dimension/fact table. Their plans remain appropriate; most growth is below the roughly 20× row growth because PostgreSQL uses index-only scans, bitmap scans, hashing, and parallelism.
- **Grew more than 25×:** R12, R18, R21, W04, W05. R12, R18 and R21 remain comfortably inside their targets; their ratios combine more matching rows with cold-page variance. W05's first run was cold (2,828.853 ms) while runs 2–3 were 649.963/683.035 ms, but its required three-run average still passes. W04 performs 424,960 physical inserts and is the only target miss.

## 4. What broke at scale: W04 monthly billing

On seed data W04 averaged 189.816 ms; on large data it averaged 5,666.135 ms (29.9×) and missed the 2,000 ms target. This is not a bad read plan: the Hash Join that finds 424,960 active accounts takes only about 159–174 ms. Run 1 spends 3,601.546 ms inserting rows, including 2,385.994 ms in 424,960 FK checks. Each row must also update the invoice PK and `(account_id, billing_period_start)` UNIQUE index.

Relevant run-1 plan excerpt:

```text
Insert on invoices (actual time=3601.546..3601.549 rows=0 loops=1)
  -> Hash Join (actual time=0.054..158.858 rows=424960 loops=1)
Trigger for constraint invoices_account_id_fkey: time=2385.994 calls=424960
Execution Time: 6007.437 ms
```

Adding an index cannot remove the required inserts, FK validation, or uniqueness checks, and disabling durability/constraints would make the comparison dishonest. The production fix is to run billing as an asynchronous batch split into idempotent account-id ranges (for example 10,000 accounts per job), record job progress, and partition `invoices` by `billing_period_start` so each month's local indexes stay smaller. This preserves the result while meeting a per-batch latency target; the full 424,960-row job is throughput work and should not be treated as a single interactive request.

## 6. Partitioning proof

`sql/08_partitioning.sql` builds a non-destructive monthly RANGE-partitioned copy of `viewing_activity` on `started_at`. The large proof is saved in `benchmarks/results/large/partitioning.txt`: 4,012,819 original rows = 4,012,819 partitioned rows, zero DEFAULT rows, and zero `EXCEPT ALL` differences.

- The one-day R03-shaped predicate scanned only `viewing_activity_y2026m06` (one monthly partition).
- The `started_at >= '2026-01-01' AND < '2027-01-01'` predicate scanned only the seven 2026 partitions plus the empty DEFAULT partition and finished in 99.474 ms in the proof.
- The non-sargable `EXTRACT(YEAR FROM started_at)=2026` counter-example scanned all 20 partitions and finished in 308.635 ms. This proves partitioning only helps when the date predicate exposes the key.
- PostgreSQL requires every PRIMARY KEY/UNIQUE constraint on a partitioned table to include the partition key, so the demo uses `PRIMARY KEY (view_id, started_at)`. No table references viewing activity, so this does not break an incoming FK.

## 7. Architecture for 100× scale

### Sharding

Shard by **account_id**, with `profile_id → account_id` routing metadata. Account/profile operations and Continue Watching stay on one shard; sharding by title would scatter a member's history across many shards. Top 10, genre analytics and Originals reports become cross-shard: each shard computes a partial aggregate, then a coordinator merges counts/max timestamps. Materialized daily aggregates avoid fan-out for dashboards.

### Read replicas and caching

- **Primary:** R01, R06, R10, R21, R24 and W01–W05 because playback/account/billing state must be current.
- **Replica:** R08, R09, R12, R14–R20 and R23; seconds of replication lag are acceptable for analytics/support.
- **Replica + cache:** R03 Top 10, R04 genre rows, R05 search, R07 next episode, R13 unwatched episodes, R22 leaving soon and R25 recommendations. Cache by locale/profile maturity where relevant and invalidate on catalog publication; use short TTLs for Top 10.

### Maintenance

Create next month's partition before month-end; detach/archive old months instead of deleting millions of rows. Give `viewing_activity` lower autovacuum scale factors than small tables, monitor dead tuples and index bloat, and run `ANALYZE` after bulk loads. Refresh daily/hourly summary tables for Top 10 and heavy reports. Keep billing jobs idempotent with the existing account-period UNIQUE constraint and retry by batch.

## 8. Conclusion

The optimized design is ready for the supplied next-year volume: 29/30 latency targets pass, all member-facing queries pass, results remain protected by constraints, and monthly partition pruning is proven on all 4.01M view rows. Remaining risks are the single-transaction W04 batch, the two source-data quality violations, storage growth near 20×, and cross-shard analytics at 100×. The batching, validation, partitioning, replica, cache and aggregate strategy above addresses those risks without weakening correctness.
