## 3. Write overhead

| Write | Before (ms) | After (ms) | Change | Indexes it must maintain |
|---|---:|---:|---:|---|
| W01 | 1.148 | 3.523 | +206.9% | viewing_activity: idx_va_profile_title_started, idx_va_started_cover, idx_va_episode_notnull |
| W02 | 2.190 | 2.276 | +3.9% | my_list: idx_my_list_added_at |
| W03 | 1.453 | 1.572 | +8.2% | accounts: none of the new ones (plan_id is not indexed; HOT update possible) |
| W04 | 155.279 | 189.816 | +22.2% | invoices: none (new rows are PAID, idx_invoices_failed_period_account holds only FAILED) |
| W05 | 29.531 | 27.164 | -8.0% | accounts: idx_accounts_onhold_next_billing (rows become ON_HOLD) |

Slower after indexing: W01, W02, W03, W04. Each extra index on a table is one more B-tree insert per new row. The single-row writes (W01–W03) stay within a few milliseconds, far inside the real-time target, so the overhead is acceptable for the read speed-ups. W04 inserts PAID invoices only, which the partial FAILED index does not store, so no new index is maintained by W04; its time is the INSERT itself and the FK check on accounts. W05 uses the FAILED partial index for its EXISTS lookup.

## 5. Queries we could not (or did not need to) speed up

- **R16 (account sharing per hour):** it groups *every* viewing row by account and hour, so it must read the whole table (200k rows) whatever indexes exist; the cost is the hash joins and the `count(DISTINCT)` sort. An index cannot skip rows the query needs. The real fix would be a summary table refreshed by a nightly job, which we did not add because the report must show live data.
- **R14 (kids compliance):** reads all views of the 10,000 kids profiles (13% of all profiles). We tested; the planner keeps Seq Scan + Hash Join, which is correct for that share.
- **R15, R17:** aggregates over whole tables (all active accounts, all ratings); a Seq Scan is the cheapest way to read everything.
- **R09, R18:** read all of 2026 (about a third of viewing_activity). The rewrite removes the per-row function, but most of the table is still read.
- **R02, R06, R07, R24, R25:** already used PK/UNIQUE indexes or scanned only a small table; their baseline times were already close to 1 ms, so another index was not justified.

## 6. The wrong-result query: R13 (NULL rule)

`e.episode_id NOT IN (SELECT v.episode_id FROM viewing_activity v)` returned **0 rows**. Movie views store `episode_id = NULL`. `x NOT IN (a, b, NULL)` means `x<>a AND x<>b AND x<>NULL`, and `x<>NULL` is UNKNOWN, so the condition is never TRUE and no episode survives. `NOT EXISTS (SELECT 1 FROM viewing_activity v WHERE v.episode_id = e.episode_id)` only asks whether a matching row exists (TRUE/FALSE), so NULLs cannot break it. The correct answer is **8 unwatched episodes**, confirmed independently with `EXCEPT` below. This is the one query whose result changes, on purpose.
